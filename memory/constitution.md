# Constitution — Plataforma de Talleres Mecánicos

Convenciones no-negociables del proyecto. No se repiten en los specs individuales; se referencian desde ellos.

## 1. Arquitectura

- Stack: Laravel 13, PHP 8.4+, PostgreSQL 16+ con PostGIS.
- Marketplace público: Blade + Tailwind CSS + Alpine.js, guard `web` (provider `usuarios_marketplace`).
- ERP + Super Admin: FilamentPHP v5, guard `sistema` (provider `usuarios_sistema`). Dos paneles: `/admin` (Super Admin, solo SUPER_ADMIN) y `/erp` (por taller). (Decisión 2026-07-26: se instaló v5, no v3 — v3 no tiene compatibilidad garantizada con Laravel 13/PHP 8.5 y plugins clave del ecosistema ya no la soportan. La API de multi-tenancy/autorización difiere de v3: no usar `->tenantOwnership()` ni `->spatiePermission()`, esos métodos no existen en ninguna versión real de Filament — ver `specs/017-infraestructura-sistema/plan.md` §2.)
- Multi-tenancy: single-database, aislamiento por `taller_id`. Se implementa con trait propio `App\Traits\BelongsToTaller` (global scope `WHERE taller_id = ?` + auto-fill en `creating`), NO con `stancl/tenancy` ni `spatie/laravel-multitenancy` (overkill para este caso). El `taller_id` activo vive en la sesión del usuario autenticado. Desactivar el scope (`withoutGlobalScope()`) solo lo hace Super Admin y esa acción se audita.
- Roles/permisos: `spatie/laravel-permission` con `'teams' => true` y `'team_foreign_key' => 'taller_id'`. Roles globales tienen `taller_id = NULL`; roles por taller tienen `taller_id` seteado. Permisos son siempre globales (formato `modulo.accion`), nunca se crean por taller.
- Geolocalización: `GEOMETRY(Point,4326)` PostGIS. `lat`/`lon` son la fuente de verdad; `geom` se deriva y sincroniza automáticamente en la misma transacción vía cast propio `App\Casts\GeometryCast` + trait `App\Traits\HasGeolocation` (hook `saving`). No existe paquete PostGIS maduro para Laravel/PostgreSQL — se usa `DB::raw` con `ST_DWithin`, `ST_MakePoint`, `ST_SetSRID`, `ST_DistanceSphere`. Todo índice geoespacial es `GIST`.
- Paquetes base: `filament/filament` v5, `spatie/laravel-permission` v7, `laravel/socialite` (login Google marketplace), `laravel/breeze` (scaffolding auth marketplace, sin password — se redirige a Google), Leaflet custom (mapas Blade), `spatie/laravel-activitylog` v5 (auditoría genérica de modelos), `spatie/laravel-sluggable` (slugs), `Storage::putFile()` en MVP (logo de taller, avatar), `spatie/simple-excel` (exportaciones — reemplaza a `maatwebsite/laravel-excel`/`pxlrbt/filament-excel`: no instalables en PHP 8.5, ver `specs/017-infraestructura-sistema/plan.md` §1), `laravel/sanctum` (reservado para API futura, no crítico en MVP).
- Logos y avatares: se usa `Storage::putFile()` (disco `public`), no `spatie/medialibrary`. Simplemente se guarda la ruta en la columna `logo_url`/`avatar_url`. En producción, disco `s3`.
- Descartados y por qué: `stancl/tenancy` / `spatie/laravel-multitenancy` (tenancy simple con `taller_id` alcanza), `grimzy/laravel-mysql-spatial` (es para MySQL), `laravel/cashier` (no hay pagos online en MVP), `laravel/scout` (no se necesita full-text), `laravel/jetstream` / `laravel/fortify` (Breeze + auth propia de Filament cubren el caso).
- Notificaciones: sistema nativo de Laravel (canal `database` + `mail`), sin paquete adicional.
- Validación: Form Requests nativos de Laravel. En Filament, las reglas van en el schema del formulario. Reglas de negocio (unicidad por taller, transición de estado válida) no viven en el controller — van en Form Request o en una Action/Service dedicada.
- Convención de nomenclatura: toda lógica de negocio reutilizable va en `app/Actions/{Feature}/{NombreAccion}Action.php`. Ej: `app/Actions/Ordenes/CrearOrdenTrabajoAction`, `app/Actions/Inventario/RegistrarMovimientoInventarioAction`. Excepciones: los Form Requests pueden contener validación que no es reutilizable. No existe `app/Services/` — todo es Actions.

## 2. Convenciones de datos (aplican a toda tabla nueva)

- PK: `id BIGINT GENERATED BY DEFAULT AS IDENTITY`. FK: columna `tabla_singular_id`.
- Dinero: `NUMERIC(12,2)` en Bs. Cantidades de inventario: `NUMERIC(12,3)`.
- Estados: `VARCHAR` + `CHECK (columna IN (...))`. Texto corto `VARCHAR(255)`, texto largo `TEXT`. **Nota (2026-07-26):** Laravel 13 no tiene un método fluent `$table->check(...)` en `Blueprint` (no existe en ninguna versión de Laravel pese a aparecer en versiones anteriores de algunos `plan.md`). Los `CHECK` se agregan con `DB::statement("ALTER TABLE tabla ADD CONSTRAINT tabla_columna_check CHECK (...)")` **después** del `Schema::create(...)`, dentro del mismo método `up()`.
- `created_at` / `updated_at`: `TIMESTAMPTZ NOT NULL DEFAULT NOW()`. `deleted_at`: `TIMESTAMPTZ NULL` solo donde el spec indique soft delete.
- Tablas de auditoría/historial son **append-only**: sin `updated_at` ni `deleted_at`, nunca se editan ni se borran, sin excepción.
- Sin acentos ni `Ñ` en nombres de tabla/columna.
- Borrado lógico (`activo = FALSE` o `deleted_at`) para: usuarios, talleres, clientes, vehículos, empleados, servicios, repuestos, proveedores, órdenes, notas, reseñas.
- Nunca borrado físico de: auditorías, historiales, movimientos de inventario, pagos, líneas de orden/nota, solicitudes completadas o rechazadas.
- Catálogos (roles, permisos, métodos de pago, unidades de medida) se desactivan, no se borran; un registro desactivado no puede usarse en operaciones nuevas pero no afecta histórico.

## 3. Reglas de negocio transversales (no repetir por feature)

1. Usuario marketplace nunca accede al ERP; usuario sistema nunca usa el marketplace. Una identidad es `MARKETPLACE` o `SISTEMA`, nunca ambas, sin excepción en el MVP.
2. Toda entidad operativa del ERP pertenece a un `taller_id`; cero lectura/escritura cruzada entre talleres salvo Super Admin (auditado).
3. Ningún usuario opera sobre un taller sin una `asignacion_rol` activa para ese taller.
4. Contraseñas: siempre hasheadas, nunca en texto plano, nunca auditadas ni logueadas.
5. Toda operación que modifique más de una entidad relacionada corre en una transacción de base de datos; si una parte falla, rollback completo, sin estados intermedios.
6. Bloqueo de fila (`SELECT ... FOR UPDATE`) obligatorio en: aprobación de solicitud de taller, movimientos de inventario (fila del repuesto), registro/anulación de pago (fila de la nota), generación de código secuencial.
7. Los totales derivados (órdenes, notas) se recalculan en la misma transacción que las líneas que los originan.
8. Los códigos operativos (orden, nota, cliente, vehículo/placa, repuesto, servicio) son únicos por `taller_id`, nunca reutilizables. Se generan con `SequentialCodeGenerator` (spec `017`).
9. Moneda única Bs, sin soporte multi-moneda. Zona horaria operativa `America/La_Paz`; toda fecha de negocio se muestra en hora local, se almacena en `TIMESTAMPTZ`. Sin facturación fiscal ni cálculo automático de impuestos en el MVP; la nota de venta es un documento interno.
10. Placa de vehículo: normalizada sin guion en BD (`ABC123`), mostrada con guion (`ABC-123`), regex `^[A-Z]{3}[0-9]{3}$`, única por taller.
11. Idempotencia: login OAuth es idempotente por `provider + provider_subject`; la aprobación de una solicitud de taller no puede ejecutarse dos veces (bloqueo + validación de estado).
12. Recálculo de calificación de taller (promedio y cantidad de reseñas): **síncrono**, en la misma transacción que la creación/edición/eliminación de la reseña. No requiere queue. Se ejecuta vía evento de modelo y listener sincrónico.
13. Soft delete de entidades operativas: cuando se soft-deletea un registro padre (cliente, vehículo, empleado, servicio, repuesto, proveedor), la operación se **bloquea** si existen registros hijos activos que dependen de él (órdenes en curso, líneas no anuladas, movimientos de inventario). Una excepción: el soft delete de un **taller** no se bloquea nunca (solo muestra advertencia), para permitir cierre administrativo del tenant.

## 4. Errores de negocio

Se devuelven siempre como `App\Exceptions\BusinessException`, que Laravel convierte a:
- **Marketplace (Blade)**: redirect back con `->withErrors()` y `->with('error', mensaje)` → el componente `<x-alert>` lo muestra.
- **ERP (Filament)**: `Notification::make()->danger()->title(...)` vía `Filament\Facades\Filament::notify()` — el Action la captura y lanza notificación toast roja.
- **API (JSON)**: respuesta 422 con `{ error: mensaje, code: 'BUSINESS_ERROR' }`.

Nunca se devuelven como excepción genérica sin manejar (500). Errores cubiertos: acceso sin rol activo al taller, rol o usuario inactivo, transición de estado inválida, stock insuficiente, código o placa duplicados, descuento o pago mayor al permitido, entidad inactiva usada en una operación nueva, latitud/longitud o geometría fuera de rango, nota anulada recibiendo pagos, método de pago inactivo, usuario bloqueado por intentos fallidos, contraseña temporal no cambiada, soft delete bloqueado por hijos activos.

## 5. UI / Design system (Marketplace, ERP, Super Admin)

- Marketplace: Blade + Tailwind + Alpine, mobile-first, SEO-friendly. ERP y Super Admin: FilamentPHP v3.
- Paleta: primario azul marino, secundario naranja/amarillo (CTA y alertas), fondos gris claro `#F3F4F6` / tarjetas blancas.
- Badges de estado por color: verde = éxito/activo/pagado/completado/entregado; amarillo-naranja = pendiente/en revisión/pausado/esperando aprobación; azul = en proceso/emitida/en diagnóstico; rojo = error/anulado/rechazado/suspendido/stock crítico; gris = inactivo/cancelado.
- Tipografía Inter o Roboto. Contraste AA, labels visibles (no solo placeholder), foco visible en navegación por teclado, atributos ARIA en controles de mapa.
- Sidebar del ERP filtrado por permiso `modulo.ver`; acceso a URL sin permiso → pantalla 403 con botón de vuelta al dashboard.
- Selector de taller activo (Tenant Switcher) en el topbar del ERP si el usuario tiene acceso a más de un taller; fijo y no editable si solo tiene uno.
- Breakpoints: móvil `<768px` (ERP en modo colapsado, tablas con scroll horizontal), tablet `768–1024px` (botones grandes, Kanban 2 columnas), escritorio `>1024px` (experiencia completa).
- Formularios: botones con spinner y disabled al enviar; tablas Filament con skeleton loading.
- Loading states en marketplace: búsqueda asíncrona (Alpine) muestra `<x-skeleton>` (bloque gris animado de altura variable) en lugar de los resultados mientras `Alpine.store('search').loading === true`. El mapa muestra un spinner centrado hasta que Leaflet carga los tiles.

## 6. Testing y calidad

- `pestphp/pest` (sintaxis `it()`/`test()`) para todos los tests. Un test por regla crítica de negocio (transición de estado, cálculo de total, aislamiento multi-tenant), no un test por línea de código.
- Cobertura mínima esperada por feature: máquina de estados, cálculo de totales, aislamiento entre talleres (un taller no puede leer/escribir datos de otro), y cada `CHECK` listado en el `plan.md` de la feature.
- `laravel/pint` antes de cada commit para estilo PSR-12 + convenciones Laravel.
- `barryvdh/laravel-debugbar` solo en desarrollo, para detectar N+1 y verificar que las queries van filtradas por `taller_id`.
- Base de datos de tests: `phpunit.xml` / `phpunit` de Pest usa `RefreshDatabase` con PostgreSQL dedicado (`.env.testing` con `DB_DATABASE=taller_test`). No se usa SQLite in-memory porque el sistema depende de PostGIS y CHECK constraints que SQLite no soporta.

## 7. Seguridad

- Nunca loggear, auditar ni exponer `password_hash`.
- El global scope de `taller_id` no se desactiva salvo `withoutGlobalScope()` explícito por Super Admin; esa acción queda auditada.
- Bloqueo por intentos fallidos: 5 intentos fallidos bloquean el usuario sistema 15 minutos o hasta desbloqueo manual por admin; login exitoso reinicia el contador.
